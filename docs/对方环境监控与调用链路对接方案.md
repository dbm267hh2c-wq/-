# 对方环境监控与调用链路对接方案

除日志（Filebeat）外，还需要监控对方的：

- 服务器本身（CPU、内存、磁盘、网卡、进程）
- 应用端口 / 服务存活
- 数据库存活与性能
- 对方应用之间、服务器之间的调用链路

**先收齐资产和调用关系，再装采集器。** 对方不提供 IP、端口、库地址和链路关系，监控无法落地。

日志采集细节见 [Filebeat对接Logstash方案.md](./Filebeat对接Logstash方案.md)。

---

## 1. 监控分层

```
                    对方必须先提供的信息
                    IP / 端口 / 库 / 调用关系
                              │
        ┌─────────────────────┼─────────────────────┐
        ▼                     ▼                     ▼
   主机与资源              端口与数据库            应用调用链
   Metricbeat             Heartbeat               APM Agent
                          + DB 模块               （埋点）
        │                     │                     │
        └──────────┬──────────┘                     │
                   ▼                                ▼
            我方 Logstash :5044              我方 APM Server
                   │                                │
                   └────────────┬───────────────────┘
                                ▼
                              Kafka
```

| 监控对象 | 采集组件 | 对方必须提供 | 送到哪里 |
| --- | --- | --- | --- |
| 应用日志 | Filebeat | 服务器 IP、日志路径 | Logstash `5044/tcp` → Kafka `beats_data` |
| 主机资源 / 进程 | Metricbeat | 服务器 IP、主机名、操作系统 | Logstash `5044/tcp` → Kafka `metric_data` |
| 应用端口存活 | Heartbeat | 应用名、协议、IP、端口、探测 URL | Logstash `5044/tcp` → Kafka `uptime_data` |
| 数据库 | Metricbeat 对应模块 | 库类型、IP、端口、库名、只读账号 | Logstash `5044/tcp` → Kafka `metric_data` |
| 应用间调用链路 | APM Agent / OTel | 服务名、语言、上下游、接口协议 | APM Server → Kafka `apm_data` |
| 静态拓扑（底图） | 对方填表，不靠采集 | 调用关系表 | 我方据此配监控和告警 |

说明：

- **Filebeat / Metricbeat / Heartbeat 都走 Beats 协议，同一端口 `172.28.65.248:5044`。**
- 调用链必须在对方应用里埋点，只靠主机监控看不到「A 调了 B」。
- 对方先交静态调用关系表，作为拓扑底图；APM 跑起来后再用真实 Trace 校验。

## 3. 采集怎么做

对方 **不要装 Logstash / ES / Kibana**。按角色装 Elastic 8.x 采集器，版本与我方 Logstash 对齐（建议 `8.19.19`）。

### 3.1 应用服务器（有日志、有端口）

安装：

1. **Filebeat**：日志，见日志对接文档。
2. **Metricbeat**：CPU / 内存 / 磁盘 / 网卡 / 进程。
3. **Heartbeat**：本机及下游端口探活（也可由我方集中部署，见 3.4）。
4. **APM Agent**：嵌在对方应用进程里，采 Trace。

### 3.2 数据库服务器

- 能装采集器：在 DB 机装 Metricbeat，启用对应模块（`mysql` / `postgresql` / `redis` 等）。
- 不能装（RDS / 托管库）：在一台能连到该库的业务机上跑 Metricbeat 远程拉指标；Heartbeat 探 `IP:端口`。

### 3.3 仅有端口、不能装 Agent 的设备

只用 Heartbeat 做 TCP/HTTP/ICMP 探测。

### 3.4 Heartbeat 部署位置

两种做法，二选一（推荐第一种）：

| 方式 | 优点 | 注意 |
| --- | --- | --- |
| 我方集中部署 Heartbeat，按对方填的 IP:端口探测 | 对方少装一个组件 | 我方到对方端口必须网络打通 |
| 对方每台机器装 Heartbeat 探本机端口 | 不依赖跨网探测 | 机器多时配置要统一 |

## 4. Metricbeat（主机 + 数据库）

### 4.1 安装（CentOS / RHEL 示例）

```bash
# 与 Filebeat 同一套 8.x 源
yum install -y metricbeat-8.19.19
metricbeat modules disable system 2>/dev/null || true
```

### 4.2 主机监控 `metricbeat.yml` 要点

```yaml
name: "请改成该服务器业务IP"          # 与 Filebeat 的 name 保持一致

metricbeat.config.modules:
  path: ${path.config}/modules.d/*.yml
  reload.enabled: false

output.elasticsearch:
  enabled: false

output.logstash:
  enabled: true
  hosts: ["172.28.65.248:5044"]

processors:
  - add_host_metadata: ~
  - copy_fields:
      fields:
        - from: agent.name
          to: host.name
      fail_on_error: false
      ignore_missing: true
  - add_fields:
      target: ''
      fields:
        beat_type: metricbeat

setup.template.enabled: false
setup.ilm.enabled: false
setup.kibana.enabled: false
```

启用系统模块：

```bash
metricbeat modules enable system
```

`modules.d/system.yml` 至少打开：

```yaml
- module: system
  period: 10s
  metricsets:
    - cpu
    - load
    - memory
    - network
    - process
    - process_summary
    - filesystem
    - fsstat
  process.include_top_n:
    by_cpu: 10
    by_memory: 10
```

### 4.3 数据库模块（按对方填表启用）

```bash
metricbeat modules enable mysql        # 或 postgresql / redis / mongodb
```

MySQL 示例 `modules.d/mysql.yml`：

```yaml
- module: mysql
  period: 10s
  hosts: ["user:password@tcp(数据库IP:3306)/"]
  metricsets: ["status", "galera_status"]
```

PostgreSQL 示例：

```yaml
- module: postgresql
  period: 10s
  hosts: ["postgres://监控用户:密码@数据库IP:5432/postgres"]
  metricsets: ["activity", "bgwriter", "database"]
```

Redis 示例：

```yaml
- module: redis
  period: 10s
  hosts: ["数据库IP:6379"]
  password: "只读或探测密码"
  metricsets: ["info", "keyspace"]
```

配置完后：

```bash
metricbeat test config
metricbeat test output
systemctl enable --now metricbeat
```

注意：

- `name` 必须和该机 Filebeat 的 `name` 相同，否则日志和指标对不上主机。
- 密码不要写进可被随便拷贝的聊天记录；落地后限制 `metricbeat.yml` 权限为 `0600`。
- 不要打开 `output.elasticsearch`。

## 5. Heartbeat（应用端口 / 服务探活）

按「2.2 应用与端口」「2.3 数据库端口」生成 monitors。

```yaml
name: "heartbeat-对方环境"

output.elasticsearch:
  enabled: false

output.logstash:
  enabled: true
  hosts: ["172.28.65.248:5044"]

processors:
  - add_fields:
      target: ''
      fields:
        beat_type: heartbeat

heartbeat.monitors:
  - type: http
    id: order-service-health
    name: 订单服务
    urls: ["http://10.0.0.21:8080/health"]
    schedule: "@every 30s"
    timeout: 5s

  - type: tcp
    id: order-mysql
    name: 订单库
    hosts: ["10.0.0.31:3306"]
    schedule: "@every 30s"
    timeout: 5s

  - type: tcp
    id: order-redis
    name: 库存Redis
    hosts: ["10.0.0.32:6379"]
    schedule: "@every 30s"
    timeout: 5s
```

`id`、`name` 必须能对应到调用关系表里的应用名，方便和链路、日志关联。

```bash
heartbeat test config
heartbeat test output
systemctl enable --now heartbeat
```

## 6. 调用链路（APM，必做才能看到「谁调了谁」）

主机指标和端口探活 **看不到** 应用内部调用。要看链路，对方应用必须埋点。

### 6.1 对方开发需要配合的事项

| 项 | 要求 |
| --- | --- |
| 语言 / 框架 | Java / Go / Python / Node 等，按官方 APM Agent 接入 |
| `service.name` | 与调用关系表中的「应用名称」完全一致 |
| `environment` | `prod` / `test` 等，与服务器清单中的环境一致 |
| 出口 | 报到我方 APM Server（地址开通后提供），不要报对方自己的 ES |
| HTTP / RPC 头 | 保留 `traceparent`（W3C）或 Elastic `elastic-apm-traceparent`，保证跨服务串链 |
| 采样率 | 生产建议先 `0.1`～`0.2`，确认流量后再调 |
| 敏感信息 | 关闭请求体全量采集，脱敏 Header / SQL 参数 |

Java 示例（对方应用启动参数）：

```bash
java -javaagent:/opt/elastic-apm-agent.jar \
  -Delastic.apm.service_name=order-service \
  -Delastic.apm.environment=prod \
  -Delastic.apm.application_packages=com.example.order \
  -Delastic.apm.server_url=http://我方APM地址:8200 \
  -Delastic.apm.secret_token=对接后提供 \
  -Delastic.apm.transaction_sample_rate=0.2 \
  -jar order-service.jar
```

### 6.2 链路要对齐的三张表

1. **静态调用关系表（2.5）**：对方口头/文档中的「应该怎么调」。
2. **Heartbeat 端口表（2.2/2.3）**：这些端口必须是链路上的节点。
3. **APM `service.name`**：必须和 2.5 的应用名一致，否则拓扑对不上。

我方验收时会用 APM 真实边去核对 2.5：多出来的调用要补表，表上有但从未出现的调用要对方确认是否已下线。

### 6.3 对方暂时不能埋点时

只能提供降级能力，需书面确认：

- 有端口存活，无耗时、无错误堆栈、无 TraceID。
- 可用 Packetbeat / 流量镜像看 TCP 连接对，但看不到业务接口和数据库 SQL。
- **静态调用关系表仍然必须提供**，否则告警无法归属到业务链。

## 7. 我方 Logstash / Kafka 怎么分流

三种 Beats 都进 `5044`，用 `beat_type` / `agent.type` 分到不同 Topic。  
现有日志管道会 `remove_field => ["agent"]`，**必须先分流，再删字段**。

```conf
filter {
  if [beat_type] == "metricbeat" or [agent][type] == "metricbeat" {
    mutate { add_field => { "[@metadata][kafka_topic]" => "metric_data" } }
  } else if [beat_type] == "heartbeat" or [agent][type] == "heartbeat" {
    mutate { add_field => { "[@metadata][kafka_topic]" => "uptime_data" } }
  } else {
    mutate { add_field => { "[@metadata][kafka_topic]" => "beats_data" } }
  }
}

output {
  kafka {
    codec => json
    bootstrap_servers => "192.168.58.201:9092"
    topic_id => "%{[@metadata][kafka_topic]}"
  }
}
```

APM 数据不走 Beats 5044，走独立 APM Server，写入 Kafka `apm_data`。

## 9. 常见问题

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| 只有日志，没有 CPU/内存 | 没装 Metricbeat，或没 enable `system` | 按第 4 节安装 |
| 端口明明挂了没有告警 | 没提供端口，或 Heartbeat 未配该 monitor | 补 2.2 表并下发配置 |
| 数据库只能 ping 通，没有连接数/慢查询 | 没给只读账号，只做了 TCP 探测 | 补 2.3 并启用对应 module |
| 看不到 A 调 B | 没埋 APM，或 `service.name` 不一致 | 按第 6 节接探针并对齐名称 |
| 指标和日志对不上同一台机 | Filebeat 与 Metricbeat 的 `name` 不同 | 统一成业务 IP |
| 调用关系表和 APM 对不上 | 表是旧架构 / 有未登记的隐式调用 | 以 APM 为准回写表格 |

## 10. 对接顺序（建议）

1. 对方填完第 2 节全部表格（尤其是 **2.5 调用链路**）。
2. 网络放行 `5044/tcp`，先接 Filebeat 日志。
3. 按服务器清单装 Metricbeat，按数据库表开模块。
4. 按端口表部署 Heartbeat。
5. 核心应用接 APM，用真实 Trace 回核调用关系表。
6. 我方按链路配告警：端口失败、库连接打满、Trace 错误率、主机磁盘。
